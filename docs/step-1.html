실기기 접근성 + 라이브 스키마 스파이크 최우선

목표 미검증 항목(§2.4)을 코드 작성 전에 닫는다. 여기서 막히면 이후가 전부 무의미하다.

선행 조건 없음 — 프로젝트 부트스트랩보다 먼저 한다.

세부 단계

  1. DS-001 실기기/에뮬레이터 접근성 확인§2.1 · §10 리스크
    • OkHttp로 /unique-tournament/11204/seasons 호출
    • 모바일 네트워크 + Wi-Fi 양쪽에서 상태 코드 확인
    • 403이면 즉시 중단하고 보조 소스(naver)로 재설계 판단
  2. DS-002 게임 데이 라이브 관측 (3시간)§2.4 · §7.1
    • /sport/baseball/events/live를 30초 간격 기록
    • 확정: 라이브 status.code/description, 진행 중 innings 맵 형태, time 필드, 갱신 지연, winnerCode 무승부 값, feedLocked 전환
    • 특히 라이브 응답에 innings가 포함되는지 확인 (§7.1 폴링 설계가 여기 달림)
  3. DS-003 응답 헤더 조사§5.2
    • ETag / Cache-Control / Last-Modified 지원 여부
    • 지원되면 조건부 요청으로 라이브 폴링 트래픽 절감
  4. DS-004 프리페치 페이지네이션 확인§3.2
    • /events/next/{page} page 0→N 종료 조건
    • 총 경기 수가 720에 수렴하는지
  5. DS-005 fixture 저장§9 테스트
    • app/src/test/resources/fixtures/에 예정/라이브/종료/연장/취소 각 1건 이상

완료 조건

  • §3.4 함정 7개 + DS-002 신규 발견 항목이 전부 fixture로 고정됨
